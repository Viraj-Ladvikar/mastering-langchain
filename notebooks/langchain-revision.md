# LangChain Interview Preparation Guide

This guide is structured to help you prepare for LangChain interviews, focusing on the updated v1 framework. It breaks down concepts into common interview themes, conceptual questions, and "Why/When to use" scenarios based on real-world implementations.

---

## 1. Fundamentals & Ecosystem

**Q: What is the difference between a standalone LLM and an Agent?**
* **Standalone LLM:** Takes an input (prompt) and generates an output based on its training data. It has a "knowledge cutoff" and cannot access real-time or external data.
* **Agent:** An LLM connected to external "Tools". It acts autonomously by taking an input, deciding *which* tool to call to fetch missing context (e.g., current news, database records), and then generating an output based on the newly retrieved context. 

**Q: How do you manage Python environments efficiently for LangChain projects?**
* The modern approach is using **`uv`**, an extremely fast Python package and project manager written in Rust. It simplifies environment creation (`uv venv`) and dependency management (`uv add langchain`).

## 2. Model Interaction: Streaming vs. Batch

**Q: When would you use `model.stream()` vs `model.invoke()`?**
* **`invoke()`:** Waits until the LLM has generated the *entire* response before returning it. It is blocking and can lead to poor user experience if the response is long.
* **`stream()`:** Yields output chunks as they are generated by the LLM. 
* **Interview Scenario:** If you are building a real-time chatbot, you **must** use `stream()` so the user sees the answer being typed out progressively.

**Q: What is Batch Processing and how does it reduce costs/time?**
* `model.batch()` allows you to send a collection of independent requests to the model in parallel. By setting a `max_concurrency` config, you can process multiple user queries at once instead of sequentially, improving performance and throughput.

## 3. Mastering Tools

**Q: How does an LLM know *when* and *how* to use a Tool?**
* When creating a tool (e.g., using the `@tool` decorator in LangChain), you provide a function name, type hints, and a **docstring** (schema description). 
* When the tool is bound to the model (`model.bind_tools([tool_name])`), this schema is passed to the LLM. The LLM relies heavily on the **docstring description** to reason whether the user's prompt requires this specific tool.

**Q: Describe the Tool Execution Loop.**
1. **User Input:** User asks a question (e.g., "Weather in New York?").
2. **AI Decision:** The LLM realizes it lacks this info, returns an `AIMessage` containing a `tool_call`.
3. **Tool Execution:** The application code intercepts the tool call, executes the actual Python function (`get_weather.invoke(tool_call)`), and gets the result (context).
4. **Tool Message:** The result is appended to the conversation history as a `ToolMessage`.
5. **Final Output:** The LLM reads the `ToolMessage` and generates the final human-readable answer.

## 4. Message Structures

**Q: What are the different types of messages in LangChain and what is their purpose?**
* **`SystemMessage`**: Provides instructions/context on how the LLM should behave (e.g., "You are a senior Python developer"). Detailed system messages drastically improve output quality.
* **`HumanMessage`**: Represents the input from the human user.
* **`AIMessage`**: The response generated by the model (can be text or a tool call request).
* **`ToolMessage`**: Represents the output generated by executing a tool.

**Q: Text Prompts vs. Message Prompts?**
* **Text Prompts:** Simple strings used for straightforward, single-turn generations without history.
* **Message Prompts:** Passing a `list` of Message objects. Essential for chat applications where you need to maintain conversation history.

## 5. Enforcing Structured Output

**Q: Why do we need Structured Output from an LLM?**
* In production, you often need the LLM's response to be easily parsed by upstream application logic (e.g., extracting data into JSON to save to a database). A plain text response is too unpredictable.

**Q: Compare Pydantic, TypedDict, and DataClasses for structured output.**
* **Pydantic (`BaseModel`):** The gold standard. It enforces strict **runtime field validation** (e.g., if a field must be an `int`, and the LLM returns a `string` that can't be cast, Pydantic throws an error). It also supports nested structures (e.g., a list of `Actor` models inside a `Movie` model).
* **TypedDict:** A lightweight alternative using standard Python typing. It is equivalent to a plain dictionary at runtime, meaning **no runtime validation** occurs. Use this if you just want to guide the LLM's schema but don't strictly require type enforcement.
* **DataClasses:** A built-in Python alternative to Pydantic (available since Python 3.7). It structures data but lacks the robust out-of-the-box data validation of Pydantic. 

*Implementation:* `model.with_structured_output(SchemaClass)`

## 6. Advanced Agent Control: Middleware

**Q: What is Middleware in LangChain agents?**
* Middleware exposes "hooks" (trigger points) before/after model calls, tool executions, or agent loops. It allows you to tightly control agent behavior for logging, analytics, rate limiting, and fallbacks.

**Q: How would you handle a conversation history that grows too large and exceeds the LLM's token limit?**
* Use **`SummarizationMiddleware`**. It tracks the conversation size.
* You can configure **Triggers**: e.g., trigger summarization when `messages > 10` or `tokens > 550` or `fraction > 0.5` of the context window.
* When triggered, it uses a smaller/cheaper LLM to summarize the older conversation context, replacing older messages with the summary while keeping the most recent `N` messages intact.

**Q: How do you prevent an autonomous agent from performing a dangerous action (like transferring money or sending an email)?**
* Use **`HumanInTheLoopMiddleware`**.
* You configure it to `interrupt_on` specific high-stakes tools (e.g., `interrupt_on={"send_email_tool": ["approve", "edit", "reject"]}`).
* When the agent tries to call this tool, execution pauses. 
* A human reviews the action and issues a `Command(resume={"decision": "approve"})` to let it proceed, `"reject"` to stop it, or `"edit"` to modify the tool arguments (e.g., fixing a wrong email address) before execution.

## 7. LCEL (LangChain Expression Language)

**Q: What is LCEL and why should I use it instead of standard Python code?**
* **LCEL** is a declarative syntax using the pipe operator (`|`) to compose chains (e.g., `prompt | model | parser`).
* **Why use it?** It gives you best-in-class streaming, async support, and parallel execution (via `RunnableParallel`) right out of the box with zero extra boilerplate. It also establishes a unified `Runnable` interface for every component.

**Q: How do you pass dynamic data into an LCEL chain?**
* You use **`RunnablePassthrough`**. It allows you to inject data (like retrieved documents from a database function) into the dictionary before it reaches the prompt template.

## 8. What's Next? (Advanced Topics)
To become a top-tier LangChain developer, the next critical areas to master are:
* **RAG (Retrieval-Augmented Generation):** Loading documents, splitting text, creating embeddings, and retrieving from vector databases (Chroma, FAISS) to give LLMs private context.
* **LangGraph:** The new standard framework for building complex, stateful, cyclic, and multi-actor agents.
